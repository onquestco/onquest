### Should fix

S1. **A blog failure takes down the whole of Explore** (`features/explore/getExplore.ts`: `if (trending.error || chips.error || blogs.error) throw`).
- Explore is a signed-out entry point (OQ-16), and blogs are a secondary section of it.
- If `list_explore_blogs` errors, Explore shows its error state. That happens if the code reaches production before migration 17, or if blog card data is ever malformed.
- Fix: treat a blogs error as `blogs: []` (and leave it out of the cached value, so a hiccup isn't cached for 5 minutes).
- The same thinking applies to `getFeedPage` (now `list_home_feed`). There it's acceptable, because the feed already has its own "couldn't load" state.

S2. **BL-01 review S3 is still open, and now live in production** (`20261123194231_16_blogs.sql`: `save_blog_draft` l.376, `publish_blog` l.410, `set_blog_visibility` l.486, `set_blog_comments` l.512). A null `p_based_on` skips the OQ409 check. Migration 16 is applied, so the fix is a new migration with `if p_based_on is null or …` in all four functions, plus the four Quest equivalents from migration 9. Open a tracked task; it doesn't block BL-02.

S3. **`notification_sent.target` is documented but nothing sends it.** The taxonomy CSV gains `target: quest | blog` (spec §10), but no TypeScript code fires `notification_sent`, for Quests or blogs: `grep` finds it only in `lib/analytics/taxonomy.ts` and the CSVs, even though the CSV says "Pass · fired 16×". Either wire it where the bell row and email are made (`notifyQuestOwner`, `notifyBlogOwner`, `notifyFollowed`), or mark the CSV row "not fired" so the dashboard isn't trusted. That is a pre-existing gap, now extended.

### Notes

N1. **The `notifications` change on a live table** (l.55–60):
- `add column blog_key uuid` (no default) is metadata only.
- The FK is `deferrable initially deferred` and validates existing rows. All of them are null, so that is quick, under SHARE ROW EXCLUSIVE on `notifications` and `blogs`.
- The `check (trip_key is null or blog_key is null)` scans the table under ACCESS EXCLUSIVE, held until the whole migration commits.
- `create index` without `concurrently` blocks writes while it builds.
- At friends-test size this is a pause of under a second for likes, comments and the bell. For the next change to a big live table, use `add constraint … not valid` then `validate constraint`, and `create index concurrently` in its own migration.

N2. **Explore and profile cache keys** (`['explore','with-blogs']`, `['profile','with-blogs',…]`): correct and needed.
- New code never reads an old-shape cache entry without `blogs` (which BL-05 would crash on), and the tags are unchanged, so `updateTag(profileTag)` and `EXPLORE_TAG` still clear both.
- On rollback, the old code reads its old keys, which the same tags keep fresh.
- The orphaned old entries are harmless.

N3. **HomeFeed skipping blog items** (`features/home/feedItems.ts`, `HomeFeed.tsx`): correct on the first page and on "Load more".
- `nextOffset` still counts blog items, so paging doesn't skip or repeat.
- One edge case: a first page made only of blogs would render as an empty feed with "Load more" available. That can't happen in production before BL-05, under the runbook's no-grant rule. BL-05 removes the filter.
- An old tab on the previous build parsing new `/api/feed` pages: Quest items carry an extra `type`, which zod strips; a blog item would fail the parse. That is accepted (spec §8, deploy skew) and moot with no production blogs.

N4. **The three analytics events** (`blog_draft_saved`, `blog_published`, `blog_managed`) are wired as BL-01 review S4 asked:
- `saveBlogDraft` fires `blog_draft_saved` through `shouldTrackDraftSave`.
- `publishBlog` fires `blog_published` on the first Post and `blog_managed{edit}` on later ones.
- `setBlogVisibility`, `setBlogComments` and `deleteBlog` fire `blog_managed`.
- All run in `after()`. Properties are sizes, counts and choices only: `charsBucket` counts code points, and `blog_comment_posted.length` uses `[...body].length`.
- `blog_liked` and `blog_comment_posted` are wired too. The client events are only defined, which is right for BL-03 to BL-05.
- `minutes_since_start` is left out when the draft has no `startedAt`.

N5. **Changing `feed.test.ts` from a fixed date to the real clock** (`NOW = new Date().toISOString()`): accepted.
- `list_trending_quests` filters on the database's `now()` (last 14 days), so a fixed date from 10 Nov stopped matching once 14 days had passed. CI on `main` would have failed from 24 Nov anyway.
- The tests use relative `hoursAgo()` offsets from `NOW`, so they stay deterministic.
- A later improvement: give `list_trending_quests` a `p_now` argument with a default (additive), so tests can pin the time.

N6. **Dynamic SQL in `search_public`** (l.425–451): safe.
- Every `execute` uses a constant `$q$…$q$` body with `using query, pattern, max_rows`. User text is never concatenated into SQL.
- `%`, `_` and `\` are escaped before the `ILIKE` (backslash is the default escape character).
- Blogs match on `search_text ilike` only and rank by similarity on title + place, as spec §3.5 says.
- Tests cover body-word and place-name matches, non-public exclusion and `%%`.

N7. **The shared comment rate limit** (D13): `post_blog_comment` and the replaced `post_comment` both take `pg_advisory_xact_lock(hashtext('comment/' || user))` and count both tables. Two simultaneous posts therefore serialise, and the limit holds both ways. `blogSocial.test.ts` covers 5 Quest → blog refused and 5 blog → Quest refused.

N8. **`get_my_blog_state` owner-only fields:**
- The `left join blogs mine on … owner_key = auth.uid()` means `saved_at`, `visibility`, `comments_on`, `linked_quest_hidden` and `own_linked_quest` appear only for the writer.
- A reader gets `{liked, is_owner:false}`; `blogSocial.test.ts` l.163 checks this.
- `own_linked_quest` is limited to the writer's own trip, and is present only when `get_blog_quest` would hide it from readers (D12).
- `blogViewer.ts` also copies owner fields only when `is_owner`.

N9. **A writer can like their own draft or private blog**, because `can_see_blog` allows the owner. That mirrors `can_see_trip` and `set_like`, and doesn't notify. Later it counts in `like_count`. Same as Quests, so not a regression.

N10. **The migration 16 filename on `main` is `20261123194231_16_blogs.sql`**, not the spec's `20261124100000_16_blogs.sql`. Order is preserved (17 is `20261124110000`). Update the spec §5 and LLD references in a later docs pass.
